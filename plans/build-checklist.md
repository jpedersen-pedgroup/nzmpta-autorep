- [x] ✅ **Automatic sync on reconnect** (PRD story 34; `Client/sync/autoSync.ts`) — when there are `local-only` tests, a sync starts by itself on page load, the online event, tab focus, and signing back in; backs off 30 s → 15 min on failure; waits for sign-in on a lapsed session. - [x] ✅ **Sync reconciliation (contracted, PRD §Decisions)** — built with O2 (Oct 2026). Every edit is a new version, so the collision is two versions replacing the same one (a tester's offline edit and an administrator's online edit). A signed-off version arriving second gets a 409 from `POST /api/sync/tests` carrying the base and the head; the tester's device combines them field by field (`Client/versioning/merge.ts` — calculated readings recomputed, worded record with the overlaps) and sends the pair to `POST /api/sync/tests/merge`, which stores both originals plus the combined version (`MergedFromClientId`) — whose analyser PDF points at the stored copy of whichever of the two it carries. Overlapping fields: the version that reached the server last wins (decided by Josh, 7 Oct 2026). An unfinished tester version is stored as usual and combined when signed off. A `SyncConflict` row records each collision (pending → merged, overlapping fields worked out by the server). A `SuccessorStamp` concurrency token stops two writers both replacing one version. The device shows a non-blocking notice on the combined version and on an unfinished version an admin has edited meanwhile. *Departure:* the merge runs in TypeScript on the device, not in a .NET "Sync Reconciliation Engine", because the calculated readings and the amendment wording live there; the server validates the chain and stores every state. Covered by `SyncReconciliationTests`, `PayloadUnitsTests`, `merge.test.ts`, `syncClient.reconcile.test.ts`. Administrators see them on the admin list ("Has conflicts" filter, "Conflict" badge) and in the audit panel's "Sync conflicts" section (see O2).

## Decisions and open items (for NZMPTA / Josh)
- **Admin test editing — decided by Josh, 7 Oct 2026:** an admin's version carries the **original tester's** id (so it reaches their device and history; the admin is the amendment's author); **a reason is required** for every admin edit, both roles; admins edit **completed tests only**, both roles; and colliding versions are **merged automatically, the version that reached the server last winning** where both changed the same field (the PRD's rule), every version kept and the collision recorded.
- **Editing migrated tests** — not built: a migrated test reprints from its as-recorded verdicts, so an edit would need a conversion and a rule for what happens to a verdict whose reading changes. The viewer says it can't be edited. Decide whether NZMPTA needs this.
- **An admin version's dates** — it keeps the test's completion date (the report's "Tested" date, the list order); when it was edited is in the amendment history. A tester's own amendment, by contrast, has always been re-signed off and moves the "Tested" date to its sign-off. Confirm both are what NZMPTA wants printed.
- **Soft-delete scope** — built for a test in any state, not only completed ones as PRD §Decisions words it, so an abandoned draft that reached the server can be removed too; and with a **Restore** the PRD doesn't mention. Confirm both, or restrict delete to completed tests.
- **Attestations as the PRD describes them** — the PRD's data model has `ChecklistAttestation` rows with an actor; they're held in the test's payload instead, always the tester's (an administrator's edit carries them over and never adds one), which is what the audit panel reads. The panel can say which sections were confirmed in bulk and which items were set individually, but not whether an OK item in a bulk-confirmed section was also ticked by hand. Confirm that answers PRD 69.
